걸음여행은 국내의 다양한 명소와 걷기 좋은 길을 발견할 수 있도록, 개별 장소뿐 아니라 도보 경로를 선형 데이터로 저장하고 지도에 시각화하는 서비스입니다. 장소의 위치에 더해 그 사이를 어떻게 걸을 수 있는지 보여주려는 목적에서 출발했습니다.

2인 팀에서 서비스를 공동 기획했고, 나는 도메인 설계와 개발 전반을 주도했습니다. 팀원은 사업자등록 등 사업·운영을 맡았습니다. 백엔드를 주력으로 개발하면서 제품에 필요한 앱 기능까지 연결했습니다.

이 제품 목적은 서버 모델에도 영향을 줬습니다. 장소 목록만 저장해서는 걷는 순서, 경로 길이, 중간 저장과 재개, 완주의 의미를 설명할 수 없습니다. 경로를 저장하는 방식부터 코스·구간·진행 기록의 관계를 함께 설계해야 했습니다.

아래 좌표·코스 이름과 코드 예제는 새로 만든 합성 자료입니다. 실제 여행 코스나 사용자의 위치 기록을 공개하지 않습니다.

## 장소는 발견 지점이고, 경로는 걷는 경험이다

지도에 장소 A와 B를 표시해도 두 지점 사이의 보행 경로는 알 수 없습니다. 실제로는 강을 돌아가거나 중간 명소를 지나갈 수 있습니다.

```text
장소 모델
  A                  B

경로 모델
  A ── 중간 지점 ── C
                   │
                   B
```

경로에는 좌표의 순서가 있습니다. 같은 점들을 반대로 연결하면 걷는 방향도 달라집니다. 전체 길이와 중간 지점의 위치도 이 순서 위에서 해석해야 합니다.

이 때문에 도보 경로를 선형 데이터로 저장하고 지도에 그리도록 구성했습니다. 장소는 그 경로 주변에서 발견할 수 있는 정보로 연결합니다.

GeoJSON의 `LineString`은 순서가 있는 좌표 배열로 선을 표현합니다. 좌표는 경도·위도 순서이며, 각도 단위의 좌표 차이를 그대로 미터 거리로 해석할 수는 없습니다. [GeoJSON RFC 7946](https://datatracker.ietf.org/doc/html/rfc7946)

```json
{
  "type": "Feature",
  "properties": {
    "courseKey": "demo-walk",
    "direction": "forward"
  },
  "geometry": {
    "type": "LineString",
    "coordinates": [
      [127.0000, 37.0000],
      [127.0010, 37.0000],
      [127.0010, 37.0010]
    ]
  }
}
```

이 데이터는 구조 설명용입니다. 실제로 걸을 수 있는 길인지, 출입할 수 있는지는 좌표 배열만으로 확인되지 않습니다.

## 코스와 구간의 역할을 나눴다

긴 경로를 한 번의 기록으로만 표현하면 여러 날에 나눠 걷거나 중간에 쉬었다가 재개하는 경험이 불편합니다. 반대로 모든 구간을 독립 코스로 만들면 전체 코스를 완주했다는 의미가 흩어집니다.

걸음여행에서는 코스와 구간을 다른 책임으로 구분했습니다.

| 단위 | 제품에서의 역할 |
| --- | --- |
| 코스 | 발견·선택하는 전체 걷기 경험, 완주와 보상의 기준 |
| 구간 | 기록을 저장하고 다음에 이어 걷는 단위 |
| 실행 세션 | 한 번의 시작·일시정지·종료와 기록 업로드의 경계 |
| 진행 상태 | 현재 실행 화면에서 수락한 경로상의 위치 |
| 완료 기록 | 구간·코스의 유효한 완료를 판단할 근거 |

일정은 코스에서 시작하고, 기록과 재개는 구간을 기준으로 연결했습니다. 어느 날 구간 하나를 끝낸 사실과 전체 코스가 완성된 사실을 분리할 수 있습니다.

```text
코스
  ├─ 구간 1 ── 실행 세션·기록
  ├─ 구간 2 ── 실행 세션·기록
  └─ 구간 3 ── 실행 세션·기록

필요한 구간의 유효한 완료
  -> 코스 완주 판단
  -> 코스 보상
```

이 모델에서 구간을 다시 나누는 작업이 기존 사용자의 완료 기록을 삭제하는 작업이 되어서는 안 됩니다. 이전 경로와 기록의 연결 근거를 보존하는 것도 데이터 수명 설계의 일부입니다.

## 작은 팀에서는 운영 요소를 줄이고 데이터 계약에 집중했다

앱은 Expo·React Native·TypeScript로 구성하고, 백엔드는 Supabase의 인증·PostgreSQL·PostGIS·Storage·Edge Functions를 사용했습니다. 경로 데이터와 공간 연산을 DB 가까이에 두고 앱의 화면 상태와 서버의 기록을 연결했습니다.

```text
앱
  지도·경로 표시
  실행 상태
  GPS 기록 대기열
       │
       ▼
인증·서버 계약
       │
       ▼
PostgreSQL / PostGIS
  코스·구간·공간 데이터
  사용자 기록·완료 상태

서버 함수·외부 데이터 처리
  필요한 연동과 데이터 검증
```

이 구조를 택하면 별도 서버의 운영 요소를 줄일 수 있습니다. 대신 SQL 함수, 권한, migration, 설치된 앱의 계약을 계속 관리해야 합니다. 백엔드 복잡성이 사라지는 것이 아니라 데이터와 API의 경계에 집중됩니다.

PostGIS는 위치·선형 경로 등 공간 타입과 연산을 PostgreSQL에서 사용할 수 있게 합니다. [Supabase PostGIS 문서](https://supabase.com/docs/guides/database/extensions/postgis)

사용자 기록의 접근 권한과 클라이언트 화면의 캐시 소유권도 각각 검토해야 합니다. DB의 행 접근 제어와 앱의 오래된 응답 차단은 다른 경계입니다. [Supabase 행 수준 보안 문서](https://supabase.com/docs/guides/database/postgres/row-level-security)

## GPX를 지도용 선으로 바꾸는 것보다 입력 계약이 먼저였다

경로 입력에는 트랙 좌표, 중간 지점, 이름과 거리 정보가 있습니다. 파일 이름에 적힌 거리와 좌표를 기준으로 계산한 거리가 다를 수도 있습니다.

입력 생성기에서는 문자열 정규화, 연속 중복점 제거, 방향에 맞춘 좌표 정리, 중간 지점과 경로의 연결, 구간 생성을 처리했습니다. 표기 거리와 계산 거리는 의미가 다르므로 둘을 구분해 남깁니다.

생성 파이프라인을 설명하면 다음과 같습니다.

```text
GPX 원본
  -> 좌표·중간 지점 해석
  -> 입력 정규화와 방향 정리
  -> 누적 경로 길이 계산
  -> 경로 위의 구간 경계 결정
  -> 코스·구간 데이터 생성
  -> 구조·결정성 검사
```

구간 경계를 선택할 때 시간이나 거리만 맞추면 제품의 의미를 놓칠 수 있습니다. 쉬거나 재개할 수 있는 지점과 랜드마크를 고려해야 합니다. 기준이 되는 지점이 없는 곳에는 일관된 경계를 사용할 수 있습니다.

데이터 검사에서는 다음 계약을 봅니다.

- 앞 구간의 끝과 다음 구간의 시작이 같은 경계점을 공유합니다.
- 구간을 순서대로 연결하면 정규화한 전체 경로가 복원됩니다.
- 같은 입력으로 다시 생성했을 때 의도치 않은 차이가 생기지 않습니다.
- 코스 방향과 구간 순서가 일치합니다.

지도 표시를 가볍게 하려고 좌표를 단순화할 때도 이 계약을 유지해야 합니다. 경계점과 주요 지점이 사라지거나 기록 판정용 경로가 조용히 바뀌면 화면 최적화가 데이터 변경이 됩니다. 표시용 단순화와 기록 기준 경로를 더 분명하게 나누는 것은 개선 검토 대상입니다.

## 출발점과 현재 위치 사이의 직선거리는 진행률이 아니다

굽은 길에서 출발점과 현재 위치 사이의 직선거리는 실제 경로를 얼마나 따라왔는지 설명하지 못합니다. 종점 근처에 GPS가 한 번 찍혔다고 전체 경로를 걸었다는 증거도 아닙니다.

진행 표시에서는 GPS 좌표를 경로의 선분에 투영하고, 그 지점을 출발점부터의 누적 경로 거리로 바꿨습니다.

다음은 미터 단위의 작은 평면에서 선분 하나에 투영하는 새 예제입니다. 실제 위경도 처리 코드를 복사한 것이 아니며, 곡률·좌표계 변환이 필요한 지리 연산을 대체하지 않습니다.

```ts
type Point = { x: number; y: number };

function projectToSegment(a: Point, b: Point, p: Point) {
  const dx = b.x - a.x;
  const dy = b.y - a.y;
  const squaredLength = dx * dx + dy * dy;
  const raw = squaredLength === 0
    ? 0
    : ((p.x - a.x) * dx + (p.y - a.y) * dy) / squaredLength;
  const fraction = Math.max(0, Math.min(1, raw));
  const snapped = {
    x: a.x + fraction * dx,
    y: a.y + fraction * dy
  };

  return {
    snapped,
    distanceOnSegment: fraction * Math.hypot(dx, dy),
    lateralDistance: Math.hypot(p.x - snapped.x, p.y - snapped.y)
  };
}
```

앞 선분들의 길이를 더하면 경로상의 위치를 얻을 수 있습니다. 예를 들어 길이가 각각 10m인 두 선분이 직각으로 이어지고, 두 번째 선분의 중간에 있다면 전체 경로 20m 중 15m 지점입니다. 두 끝점 사이의 직선거리와는 다른 값입니다.

PostGIS의 `ST_LineLocatePoint`도 선 위의 가장 가까운 지점을 길이 비율로 표현하는 연산입니다. 이것은 개념을 이해하는 참고이며 앱이 해당 SQL 함수를 호출해 진행률을 계산한다는 설명은 아닙니다. 거리 단위와 좌표계는 별도로 확인해야 합니다. [PostGIS LineLocatePoint 문서](https://postgis.net/docs/ST_LineLocatePoint.html)

## 가까운 투영점을 고르는 것만으로는 부족했다

GPS가 크게 튀거나 경로가 교차하면 가까운 점 하나만으로 진행을 결정하기 어렵습니다.

실제 진행 계산에서는 경로에서 너무 벗어난 샘플을 거절하고, 처음 수락하는 위치와 이후 샘플의 전진 폭을 제한했습니다. 수락한 진행을 뒤로 돌리지 않고, 같은 투영점을 기준으로 지난 경로와 남은 경로를 나눠 지도에 표시합니다.

```text
GPS 샘플
  -> 경로상의 후보 위치
  -> 경로와의 거리 검사
  -> 처음 위치·전진 폭 검사
  -> 수락한 진행 상태 갱신
  -> 지난 경로 / 남은 경로 분할
```

다음 값은 합성 예제입니다.

| 이전 상태와 샘플 | 판단할 조건 |
| --- | --- |
| 경로에서 멀리 벗어난 좌표 | 진행을 바꾸지 않고 이탈 후보로 판단 |
| 첫 샘플이 종점 근처 | 시작 위치 계약에 맞는지 확인 |
| 짧은 간격에 경로 끝으로 이동 | 허용 전진 폭을 벗어나는지 확인 |
| 수락한 지점보다 뒤로 튄 좌표 | 이미 수락한 진행 표시를 되돌리지 않음 |

여기에는 한계가 있습니다. 단조롭게 증가하는 진행 표시는 화면의 흔들림을 줄이지만 실제 되돌아 걷기를 충분히 설명하지 못할 수 있습니다. 교차 구간에서는 서로 멀리 떨어진 경로 지점이 같은 장소에 있을 수도 있습니다. 긴 샘플 공백 후 정상 이동을 과도하게 거절할 가능성도 있습니다.

따라서 이 보정 규칙을 모든 GPS 오류나 위치 조작을 탐지하는 방법으로 소개하지 않습니다. 앞으로는 시간 간격과 이동 방향, 최근에 수락한 선분을 함께 쓰는 후보 선택을 검토하고, 실제 경로에서 오탐·누락을 측정해야 합니다.

## 화면의 진행과 서버의 완주 판단을 구분했다

진행선은 사용자가 지금 어디까지 왔는지 이해하기 위한 화면 상태입니다. 코스 완주와 보상은 서버의 기록·판정 책임으로 연결했습니다.

구간을 여러 세션에서 이어 걷더라도 필요한 구간의 유효한 완료가 모여야 부모 코스의 보상으로 이어지도록 설계했습니다. 클라이언트가 가진 진행 비율이나 종점 근처 좌표 하나를 그대로 최종 보상의 근거로 삼을 수는 없습니다.

서버에서 확인해야 할 계약에는 다음이 있습니다.

- 세션과 기록이 같은 사용자·코스에 속하는지
- 기록의 시각·순서·구간 범위가 판정에 맞는지
- 반복 업로드와 반복 완료 요청이 어떤 결과를 만드는지
- 이전 경로 버전의 기록을 어떻게 해석할지

API에 클라이언트 식별자가 있다는 사실만으로 이 모든 계약이 검증된 것은 아닙니다. 판정 구현과 중복 요청·계정 경계의 검사는 따로 확인해야 합니다. 이번 글의 회귀 검사 범위도 서버 전체 완료 판정을 포함하지 않습니다.

## 통신이 끊기면 기록의 순서와 소유자를 보존해야 한다

GPS 기록은 네트워크가 불안정할 때 업로드 대기열에 남길 수 있도록 구성했습니다. 세션 안에서 기록시각을 우선하고, 같은 시각에는 대기열 등록시각과 식별자를 사용해 순서를 정합니다.

```text
실제 기록
  -> 기기의 업로드 대기열
  -> 같은 세션 안에서 정렬
  -> 서버 업로드
  -> 응답에 따라 대기열 정리
```

늦게 도착한 기록을 먼저 전송하면 서버가 보는 이동 순서가 달라질 수 있습니다. 반대로 업로드 응답을 못 받았다고 바로 지워버리면 기록을 잃을 수 있습니다. 실제 처리 여부가 불명확한 반복 업로드와 대기열의 보관 상한은 별도 검증 대상입니다.

계정 화면의 스냅샷 캐시에는 소유자 검사와 세대값 검사를 적용했습니다. 로그아웃 뒤 이전 요청의 응답이 늦게 도착해도 새 세대의 캐시에 다시 쓰지 못하도록 하는 경계입니다.

```text
세대 A에서 조회 시작
  -> 로그아웃·캐시 비우기
  -> 세대 B
  -> 세대 A의 늦은 응답 도착
  -> 저장 전에 세대·소유자 검사
```

지원 범위도 구체적으로 설명해야 합니다. GPS 업로드 대기열은 영속 저장을 사용하지만 계정 화면의 스냅샷 캐시는 프로세스 메모리에 있습니다. 지도 타일, 전체 코스 다운로드, 모든 일정 편집이 오프라인에서 동작한다는 의미로 확대하지 않습니다.

## 경로 데이터는 출처와 사용 범위도 함께 관리해야 한다

경로를 만들 수 있는 파일을 찾았다고 앱에 배포할 수 있는 데이터가 확보된 것은 아닙니다. 경로, 지도 이미지, 사진, 관광정보의 출처와 저장·재표시 조건을 각각 확인해야 합니다.

생성기에는 원본의 식별 정보와 해시, 출처 관련 메타데이터를 남기는 구조가 있습니다. 같은 입력을 추적하는 데 도움이 되지만, 코드에 권리 상태를 표시하는 것만으로 실제 사용 범위가 확인되지는 않습니다.

이미지도 경로와 이름이 비슷하다는 이유로 임의 연결하면 실제 장소를 잘못 보여줄 수 있습니다. 이름·지역·경로 근접성과 후보의 유일성을 함께 확인하고, 확인되지 않은 매체를 제외할 기준이 필요합니다.

이 부분의 후속 과제는 실제 취득·제작 경위와 재사용 범위를 출처별로 대조하는 것입니다. 데이터 구조 검사가 통과했다는 결과를 기관 승인이나 현장 안전 검증으로 해석하지 않습니다.

## 확인한 범위와 다음 검증

2026-09-30 코드 검토에서 네 개 파일의 순수 회귀 테스트 29건을 재실행했고 모두 통과했습니다. 범위는 진행 계산, 공유 구간 경계, GPS 대기열 순서, 계정 화면 스냅샷 캐시입니다. 데이터 생성기의 결정성·구조 검사도 통과했습니다.

이 결과는 전체 앱이나 운영 서비스를 검증한 결과가 아닙니다. 서버의 전체 권한·완료 계약, 실제 실외 GPS, OS가 앱을 종료하는 상황, 배터리와 최종 APK의 동작을 이번 검토에서 다시 확인하지 않았습니다.

특히 백그라운드 위치 처리는 권한과 OS·기기별 종료 동작의 영향을 받습니다. Expo도 Android에서 종료된 앱이 위치 이벤트만으로 자동 재시작하지 않는 등의 제한을 설명합니다. 설정 코드가 있다는 사실과 실제 기록 지속성은 구분해서 검증해야 합니다. [Expo Location 문서](https://docs.expo.dev/versions/latest/sdk/location/)

다음 검증은 제품의 걷기 경험에 맞춰 우선순위를 두겠습니다.

1. 교차 경로·우회·되돌아 걷기를 실외에서 확인합니다.
2. 통신 단절과 재연결, 반복 업로드를 조합해 기록 손실·중복을 확인합니다.
3. 권한 회수, 앱 종료와 계정 전환 뒤 세션·대기열의 경계를 확인합니다.
4. 코스 데이터 재생성·재구간화 이후 기존 완료 기록이 유지되는지 확인합니다.
5. 출처별 사용 범위와 미디어 연결, 실제 현장의 보행 가능성을 별도로 검토합니다.

걸음여행의 개발은 장소를 지도에 표시하는 기능에서 시작해 제품을 완성하는 과정이었습니다. 경로를 선으로 저장한다는 기획을 코스와 구간, 진행 기록과 완주 판단의 계약으로 구체화하면서 서버와 앱을 함께 연결했습니다. 백엔드의 도메인 설계가 사용자가 걷는 경험으로 드러나게 만든 작업입니다.
