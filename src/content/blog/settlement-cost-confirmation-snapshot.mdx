미니쉬테크놀로지에서 정산 시스템의 전반적인 아키텍처 설계와 핵심 도메인 구현을 주도했습니다. 클럽미니쉬 이벤트와 함께 내가 가장 많이 맡은 영역입니다.

처음부터 신경 쓴 문제는 데이터를 계산하는 것에만 있지 않았습니다. 검토 중인 입력은 바뀔 수 있지만 확정한 결과는 당시 근거로 설명할 수 있어야 했습니다. 외부 연동에서는 서버가 응답을 받지 못한 상황과 실제 업무가 실패한 상황도 구분해야 했습니다.

이 때문에 계산, 단계별 확정, 과거 결과의 보존, 외부 처리의 결과 확인을 서로 다른 책임으로 나눴습니다. 이 글은 그 설계 판단을 일반화한 회고입니다. 아래 이름·상태·값·코드는 설명을 위해 새로 만든 합성 예제이며 실제 업무 수식과 스키마를 재현하지 않습니다.

## 계산 서비스 하나로 묶으면 서로 다른 수명이 섞인다

가상의 시스템에서 작업 내역을 모아 결과를 계산하고, 담당자가 검토한 뒤 확정하며, 확정 결과를 외부 시스템에 전달한다고 하겠습니다.

```text
원천 입력·기준정보
  -> 계산·미리보기
  -> 검토·확정
  -> 확정 결과 보관
  -> 외부 처리 요청
  -> 결과 확인
```

이 모든 작업을 하나의 거대한 서비스로 처리하면 변경 이유가 섞입니다. 계산 기준이 바뀌었는데 외부 요청 처리까지 수정하거나, 외부 재시도 로직이 과거 확정 결과를 다시 계산하는 일이 생길 수 있습니다.

실제 시스템에서는 단계별 확정과 변경 제한을 모델에 포함하고, 기준정보와 확정 스냅샷, 외부 요청의 중복 검증과 결과 확인을 구분했습니다. 책임을 설명용으로 정리하면 다음과 같습니다.

| 책임 | 변경·실패를 판단하는 기준 |
| --- | --- |
| 입력과 기준정보 | 어떤 날짜·대상에 어떤 기준을 적용하는가 |
| 계산 | 같은 입력을 같은 규칙으로 해석하는가 |
| 확정 | 현재 상태에서 이 결과를 확정해도 되는가 |
| 스냅샷 | 무엇을 당시의 근거로 보존해야 하는가 |
| 외부 처리 | 요청이 전달됐는가, 실제 결과를 확인했는가 |

이 분리는 서비스 개수를 늘리는 목적이 아닙니다. 원본을 다시 읽어야 하는 동작과 과거 기록을 읽어야 하는 동작이 같은 저장 책임을 갖지 않게 만드는 기준입니다.

## 단계별 확정은 변경 가능 구간을 정하는 모델이다

확정을 단순한 `confirmed = true`로 표현하면 어느 입력까지 바꿀 수 있는지 알기 어렵습니다. 앞선 단계의 입력을 수정했을 때 뒤 단계의 결과가 유효한지도 따로 판단해야 합니다.

실제 작업에서는 단계별 확정 과정과 동시성·변경 제한을 구현했습니다. 중요한 것은 API 호출 허용 여부와 데이터 변경 허용 여부를 함께 보는 것입니다.

합성 예제에서는 다음 질문으로 상태를 나눌 수 있습니다.

```text
편집 가능
  -> 입력 검토 완료
  -> 결과 확정
  -> 외부 처리 대기
  -> 외부 처리 결과 확인
```

이 흐름이 회사의 실제 상태 목록은 아닙니다. 상태의 역할을 보여주는 모형입니다. 결과를 확정한 뒤 원천 입력을 바꿀 수 있다면 기존 확정 결과를 보존할지, 정정 절차를 시작할지 명시해야 합니다.

버튼을 비활성화하는 화면 처리만으로 이 규칙이 지켜지지는 않습니다. 이전 화면에서 보낸 요청이나 동시에 들어온 요청도 서버가 같은 상태 규칙으로 판단해야 합니다.

## 미리보기와 확정은 같은 규칙을 사용하지만 같은 시점은 아니다

미리보기와 저장이 각각 검증을 구현하면 화면에서는 유효했던 입력이 저장 시 다른 의미로 해석될 수 있습니다. 그래서 공통 검증과 계산 책임을 사용하고, 미리보기와 저장 결과의 정합성을 확인하는 방향으로 구성했습니다.

두 동작의 차이는 다음과 같습니다.

```text
미리보기
  -> 현재 입력을 해석·검증
  -> 계산 결과를 보여줌
  -> 아직 확정 기록이 아님

확정
  -> 현재 상태와 입력을 다시 검사
  -> 같은 검증·계산 책임 사용
  -> 확정 결과와 근거를 저장
```

공통 함수를 쓴다고 미리보기 이후의 변경까지 막히는 것은 아닙니다. 미리보기 시점에 기준정보 A를 읽었는데 확정할 때 B로 바뀌었다면, 같은 계산기에서도 결과가 달라질 수 있습니다.

따라서 계약은 “어떤 상황에서도 화면의 예전 값과 같아야 한다”보다 정확해야 합니다. 같은 입력·기준·규칙이면 결과가 같고, 그 사이 입력이 바뀌면 새 검토를 요구하거나 변경 사실을 알려야 합니다.

후속 개선으로는 미리보기에 입력 버전을 포함하고 확정 시 이를 다시 확인하는 방법을 검토할 수 있습니다. 단순 해시만 추가하면 끝나는 문제는 아닙니다. 어떤 필드가 계산 근거인지, 직렬화·정규화 방법이 무엇인지, 해당 입력의 쓰기 경로가 같은 동시성 규칙을 지키는지까지 정해야 합니다.

## 동시 확정은 상태 재조회와 저장 제약을 함께 본다

서버가 한 번 상태를 읽었다고 이후에도 그 상태가 유지되지는 않습니다. 두 요청이 모두 미확정 상태를 읽고 확정 결과를 각각 저장할 수 있습니다.

합성 예제로 가능한 두 가지 접근은 다음과 같습니다.

| 접근 | 판단 방식 | 검토할 비용 |
| --- | --- | --- |
| 비관적 잠금 | 결정에 필요한 행을 잠근 뒤 상태를 재조회 | 잠금 대기·범위·순서 |
| 낙관적 조건 갱신 | 기대한 상태·버전일 때만 상태를 변경 | 충돌 이후 재조회·재검토 |

PostgreSQL의 행 잠금은 같은 행에 대한 충돌하는 수정·잠금 요청을 트랜잭션 종료까지 조정합니다. 격리 수준에 따라 대기 뒤 갱신된 행을 보거나 오류가 날 수 있으므로 재시도 계약도 필요합니다. [PostgreSQL 명시적 잠금 문서](https://www.postgresql.org/docs/current/explicit-locking.html)

다음 SQL은 낙관적 접근을 보여주는 새 예제입니다. 실제 시스템의 잠금 구현을 그대로 옮긴 코드가 아닙니다.

```sql
-- 합성 예제: 이 상태·버전을 본 요청 하나만 전이를 수행
UPDATE demo_confirmation
SET state = 'CONFIRMED',
    version = version + 1
WHERE id = :confirmation_id
  AND state = 'REVIEWED'
  AND version = :expected_version;
```

갱신 행이 한 개일 때만 같은 트랜잭션에서 스냅샷을 저장하고, 스냅샷 저장이 실패하면 상태 전이도 롤백해야 합니다. 행이 없으면 이미 확정됐거나 상태가 바뀐 이유를 다시 읽어 처리합니다.

여기에 업무 단위의 유일성 제약을 함께 두면 중복 결과 저장을 DB에서도 방어할 수 있습니다. 다만 이 상태 행만 보호하고 기준정보를 수정하는 다른 경로가 자유롭게 움직인다면 입력까지 안정적으로 읽었다는 보장은 없습니다. 필요한 쓰기 경로가 같은 변경 프로토콜에 참여해야 합니다. [PostgreSQL 제약조건 문서](https://www.postgresql.org/docs/current/ddl-constraints.html)

내가 중요하게 본 것은 잠금 종류를 선택하는 것보다 잠금·검증·저장이 보호하는 업무 단위를 일치시키는 일이었습니다.

## 적용 시점별 기준정보와 확정 스냅샷의 수명을 나눴다

현재 기준을 수정해도 과거 확정 결과는 당시의 근거로 설명할 수 있어야 합니다. 그래서 적용 시점별 기준정보와 확정 결과 스냅샷을 구분했습니다.

합성 예제에서 기준 R1이 이전 기간에 적용됐고 R2가 이후 기간에 적용된다고 하겠습니다.

| 데이터 | 의미 | 이후 변경 시 처리 |
| --- | --- | --- |
| 적용 기간이 있는 기준정보 | 어느 날짜에 어떤 기준을 고를지 | 새 기준이나 이력으로 관리 |
| 확정 당시 입력·기준 참조 | 무엇으로 계산했는지 | 확정 근거로 보존 |
| 확정 결과 | 당시 어떤 결정을 내렸는지 | 현재 기준으로 자동 재계산하지 않음 |

ID만 저장하는 방식은 참조한 행을 덮어쓸 수 있다면 과거 값이 바뀌는 문제가 있습니다. 반대로 결과만 저장하면 나중에 “어떤 입력으로 나온 값인지” 설명하기 어렵습니다.

설명용 스냅샷은 다음과 같습니다.

```json
{
  "confirmationKey": "demo-confirmation",
  "businessDate": "2026-08-10",
  "basis": {
    "referenceKey": "demo-reference",
    "referenceVersion": "R1",
    "normalizedInput": {
      "quantity": 3
    }
  },
  "result": {
    "displayValue": "demo-calculated-result"
  }
}
```

실제 저장 항목을 나열한 스키마가 아니라 입력·기준·결과의 역할을 나타낸 예제입니다. 불변 기준 버전을 참조하는 것으로 충분한 항목과 값을 복사해야 하는 항목은 데이터의 수명에 따라 결정해야 합니다.

또한 적용일과 기록일은 다릅니다. 오늘 등록한 기준이 과거 날짜부터 적용되도록 정정될 수도 있습니다. 그렇다고 기존 확정 결과를 현재 기준으로 다시 계산해 덮으면 과거 의사결정이 사라집니다. 정정이 필요하면 원래 결과와 새 결정의 관계를 남기는 절차가 필요합니다.

계산 규칙 버전·입력 해시·정정 사유를 더 체계적으로 기록하는 것은 개선 후보입니다. 완전한 이중 시간 모델이나 불변 원장이 이미 구축됐다고 설명하지 않습니다.

## 계산 방식이 늘어났을 때 계약을 더 작은 단위로 나눴다

하나의 계약이 한 가지 계산 방식만 가진다고 가정하면 새로운 방식이 들어올 때 계약 전체에 조건문과 필드가 쌓입니다.

실제 작업에서는 복수 계산 방식을 지원하도록 계약 중심 모델을 옵션 단위로 분리하고, 이관 검증과 기존 API 호환을 구현했습니다. 여기서 어려운 부분은 새 테이블을 만드는 일보다 기존 데이터와 응답의 의미를 유지하는 일이었습니다.

공개할 수 있는 합성 전환 예제는 다음과 같습니다.

```text
이전
  Agreement ── 한 가지 계산 입력

이후의 설명 모델
  Agreement
    ├─ Option A ── 계산 방식 A의 입력
    └─ Option B ── 계산 방식 B의 입력
```

이관에서는 다음 항목을 비교해야 합니다.

- 기존 한 항목이 새 모델의 어떤 옵션에 대응하는지
- 데이터가 빠지거나 두 번 만들어지지 않는지
- 이전 조회와 새 조회가 같은 업무 의미를 표현하는지
- 잘못된 입력과 예외 응답도 호환 범위에 들어가는지
- 과거 확정 기록이 이관 이후에도 당시 근거를 유지하는지

현재 모델과 새 모델을 일정 기간 비교하고 기존 입력을 새 도메인으로 변환하는 경계를 두는 방식이 유용할 수 있습니다. 기존 필드를 즉시 삭제하거나 모든 클라이언트가 같은 날 바뀐다고 가정하는 전환은 피해야 합니다. 모든 전환을 무중단으로 완료했다는 결과를 이 글에서 주장하지는 않습니다.

## 외부 응답 실패를 업무 실패로 단정하지 않았다

외부 처리에서는 요청을 보낸 뒤 응답을 받지 못하는 구간이 있습니다. timeout이 났다고 외부 시스템이 아무 일도 하지 않았다는 뜻은 아닙니다.

```text
우리 시스템 ── 요청 전송 ──> 외부 시스템
우리 시스템 <── 응답 유실 ── 외부에서는 처리됐을 가능성
```

이 상태에서 새 업무로 즉시 재요청하면 중복 처리가 생길 수 있습니다. 따라서 요청 식별, 결과 확인, 재시도 한계와 수동 검토 상태를 구분하는 방향으로 설계했습니다.

설명용 상태 구분은 다음과 같습니다.

| 관측한 사실 | 다음에 확인할 것 |
| --- | --- |
| 외부가 처리하지 않았다고 명확히 응답 | 같은 업무의 재시도 허용 여부 |
| 응답이 없거나 결과가 불명확 | 기존 요청 식별자로 결과 확인 |
| 성공 결과를 확인 | 같은 요청을 새 업무로 다시 실행하지 않음 |
| 결과 확인도 계속 불명확 | 자동 재시도 한계와 수동 검토 |

이 표는 외부 제공자의 실제 응답 코드나 내부 운영 상태를 공개하는 표가 아닙니다. 결과 조회가 없거나 식별자로 조회할 수 없는 제공자라면 자동 복구의 범위도 달라집니다.

DB 트랜잭션과 외부 처리가 하나로 원자적이라고 가정해서는 안 됩니다. 요청 직전 중단, 외부 성공 뒤 로컬 기록 실패, 결과 조회 실패를 각각 다뤄야 합니다. 자동 재시도가 안전한지 모르는 상황에는 결과 불명확 상태를 남기는 편이 업무 의미에 맞습니다.

## Redis 중복 검증의 범위도 제한해서 설명해야 한다

실제 요청 중복 검증에서는 요청 내용의 지문과 Redis 조건부 저장·만료를 사용했습니다. 짧은 시간에 같은 요청이 겹치거나 같은 키로 다른 내용을 보내는 경우를 판단하는 경계입니다.

Redis의 `SET`은 `NX`로 키가 없을 때만 저장하고 만료 옵션을 함께 사용할 수 있습니다. 이 원자적 조건부 저장을 애플리케이션의 먼저 조회한 뒤 저장하는 흐름과 구분해야 합니다. [Redis SET 문서](https://redis.io/docs/latest/commands/set/)

하지만 만료되는 요청 키는 영속적인 업무 중복 방지와 다릅니다. 키가 만료된 뒤 같은 요청이 들어올 수 있고, 외부 성공 뒤 로컬 결과 기록이 실패할 수도 있습니다.

후속 설계에서는 다음 책임을 따로 봅니다.

```text
짧은 요청 중복 검증
  -> 동시·반복 요청 판단

영속 업무 식별·유일성
  -> 같은 확정 결과에서 새 업무를 중복 생성하는지 판단

외부 결과 확인
  -> 이미 보낸 요청이 실제로 처리됐는지 판단
```

첫 번째 구현이 있다고 뒤 두 책임까지 완성됐다고 말할 수는 없습니다. 요청 상태를 오래 보존하고 결과를 재사용하는 방식, 외부 식별자의 수명과 로컬 업무 제약을 맞추는 방식은 별도의 개선 검토 대상입니다.

## 검증과 다음 개선의 우선순위

이 회고는 구현과 변경 기록, 설계 책임 범위를 대조한 결과입니다. 회사 환경의 전체 자동화 테스트나 외부 제공자 연동을 이번 글 작성 과정에서 다시 실행하지 않았습니다. 이후 재설계 문서의 목표 구조와 현재 구현 범위도 구분합니다.

현재 설명할 수 있는 기여는 단계별 확정·변경 제한, 미리보기와 저장의 공통 검증, 적용 시점별 기준정보와 스냅샷, 옵션 단위 모델 전환과 기존 API 호환, 요청 중복 검증과 외부 결과 확인 경계입니다.

다음 개선은 업무 결과가 달라질 수 있는 실패부터 검증하겠습니다.

1. **확정 경쟁:** 두 요청을 동시에 보내 결과가 하나의 결정으로 남는지 확인합니다.
2. **입력 변경:** 미리보기 이후 기준정보를 바꿔 확정 시 재검토 계약을 확인합니다.
3. **과거 재현:** 기준을 바꿔도 과거 확정 결과의 근거가 유지되는지 확인합니다.
4. **부분 성공:** 외부 처리 성공 뒤 로컬 기록 실패를 주입해 재요청 여부를 확인합니다.
5. **이관 호환:** 정상 결과와 예외 응답, 재실행을 기존·새 모델에서 비교합니다.

배포·DB 변경의 실행 경계는 [Flyway와 일회성 migration 작업에 관한 글](/posts/flyway-ecs-one-off-migration/)에서 별도로 설명합니다. 도메인 설계와 배포 절차를 한 글에 모두 반복하기보다, 어떤 결과를 확정했는지와 그 구조를 어떻게 변경할지를 이어서 볼 수 있게 하려 합니다.

정산 아키텍처를 설계하면서 가장 중요했던 기준은 데이터가 언제 어떤 의미로 고정되는지였습니다. 바뀔 수 있는 입력, 확정된 근거, 아직 확인하지 못한 외부 결과를 구분해야 이후 정책 변경과 실패 상황에서도 같은 업무를 설명할 수 있습니다.
