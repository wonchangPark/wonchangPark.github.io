클럽미니쉬에서 이벤트와 템플릿을 설계하고 계산한 가격을 저장하면서, 이벤트 수정 이후 그 가격을 어떻게 갱신할지도 맡았습니다. 원본 변경과 파생 결과 갱신을 연결하는 데 Outbox를 사용했습니다.

가격을 저장한 배경은 [이벤트 템플릿과 읽기 모델 설계 글](/posts/event-template-centered-modeling/)에서 설명했습니다. 이 글에서는 수정 요청이 들어온 뒤 어디에서 실패할 수 있고, 어떤 기록을 남겨야 다시 시작할 수 있는지에 집중합니다. 아래 코드와 메시지 모양은 새로 만든 설명용 의사코드입니다.

## 하나의 요청 안에 서로 다른 성공 조건이 있었다

이벤트를 수정하면 저장 가격도 바뀌어야 합니다. 하지만 원본 저장과 가격 갱신은 성공 조건이 다릅니다.

원본 저장은 이벤트의 변경 가능 여부와 데이터 제약을 만족해야 합니다. 가격 갱신은 필요한 조건을 읽고 계산한 뒤 파생 결과를 저장해야 합니다. 두 작업을 같은 트랜잭션에 넣으면 즉시 일치하는 결과를 얻기 쉽지만, 계산 실패가 원본 변경의 실패로 이어집니다.

반대로 원본만 커밋한 뒤 메모리에서 계산 요청을 보내면, 그 사이 프로세스가 종료될 때 요청이 사라질 수 있습니다.

```text
원본 변경 커밋 성공
  -> 프로세스 종료
  -> 메모리에만 있던 갱신 요청 소실
```

필요했던 것은 비동기 실행 자체보다, 원본을 바꿨을 때 갱신해야 한다는 사실도 함께 저장하는 구조였습니다.

## 원본과 갱신 작업을 같은 DB 트랜잭션에 기록했다

실제 적용한 구조는 원본 변경과 Outbox 작업 저장을 같은 트랜잭션으로 묶고, 계산은 커밋 이후 별도로 수행하는 방식입니다.

```text
[원본 변경 트랜잭션]
  이벤트 변경
  갱신 작업을 Outbox에 저장
  Application event 발행
  커밋

[빠른 처리 경로]
  AFTER_COMMIT listener
  별도 트랜잭션에서 가격 갱신

[미처리 작업 경로]
  남아 있는 Outbox 작업 조회·발행
  큐 소비자가 가격 갱신
```

Application event를 발행하는 시점과 listener가 처리하는 시점은 다릅니다. 트랜잭션 안에서 이벤트를 발행하고, 트랜잭션에 연결된 listener가 커밋 이후 실행되도록 할 수 있습니다. Spring의 `@TransactionalEventListener`는 이 처리 단계를 지정하는 기능입니다. [Spring 트랜잭션 이벤트 문서](https://docs.spring.io/spring-framework/reference/data-access/transaction/event.html)

Outbox의 중요한 원자적 경계는 **원본 변경과 갱신 작업 기록**입니다. DB 저장과 외부 브로커 발행을 한 번에 원자적으로 만든다는 뜻은 아닙니다. 발행 뒤 완료 기록 전에 중단되면 같은 작업을 다시 발행할 수 있습니다. [AWS Transactional Outbox 설명](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html)

## 커밋 이후 listener는 빠른 경로이며 복구 기록은 DB에 남는다

커밋 이후 listener를 두면 원본이 커밋되기 전에 다른 실행 경로가 읽는 문제를 피할 수 있습니다. 그러나 callback을 등록했다고 프로세스 종료 후에도 실행이 이어지는 것은 아닙니다.

따라서 빠른 경로가 실행되지 않거나 실패했을 때도 Outbox를 보고 미처리 작업을 찾을 수 있어야 합니다. 큐는 그 작업을 다시 처리하는 전달 경로입니다.

| 실패 지점 | 남아야 하는 상태 |
| --- | --- |
| 원본 저장 트랜잭션 롤백 | 원본 변경과 Outbox 작업이 함께 롤백 |
| 커밋 뒤 listener 실행 전 중단 | 커밋된 원본과 미처리 작업이 남음 |
| 계산 중 예외 | 완료로 처리되지 않은 작업이 남음 |
| 계산 성공 뒤 완료 기록 실패 | 결과가 이미 반영됐을 가능성과 미처리 작업이 함께 존재 |
| 큐 발행 뒤 발행 결과 기록 실패 | 같은 작업이 다시 전달될 가능성 |

아래 두 행 때문에 “작업이 남으면 다시 실행한다”만으로 충분하지 않습니다. 소비자가 같은 업무를 다시 실행해도 결과가 훼손되지 않는지 확인해야 합니다.

이벤트 가격 갱신에는 커밋 이후 즉시 처리 경로와 큐 기반 재처리 경로를 구성했습니다. 이 사실을 모든 장애에서 복구가 완료된다거나 정확히 한 번 실행된다는 운영 보장으로 확대하지는 않습니다.

## 트랜잭션 애너테이션보다 호출 경로가 중요했다

메시지 처리 작업에서는 별도 트랜잭션이 필요했습니다. 그런데 Spring의 기본 프록시 방식에서는 같은 객체 안에서 다른 메서드를 호출하면 프록시를 통과하지 않습니다. 호출 대상에 `REQUIRES_NEW`를 붙였더라도 self-invocation이면 그 설정이 적용되지 않습니다. [Spring 선언적 트랜잭션 문서](https://docs.spring.io/spring-framework/reference/data-access/transaction/declarative/annotations.html)

설명용 예제에서 문제가 되는 모양은 다음과 같습니다.

```java
// 설명용 의사코드: 같은 객체 내부 호출
class Relay {
    void relay(Work work) {
        this.process(work);
    }

    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void process(Work work) {
        // 계산과 결과 저장
    }
}
```

이 경우를 해결하기 위해 실제 처리기를 별도 Spring bean으로 분리했습니다. 호출자가 주입받은 처리기를 호출해 트랜잭션 프록시를 지나게 했습니다.

```java
// 설명용 의사코드: 서로 다른 bean 사이의 호출
@Component
class Relay {
    private final PriceWorker worker;

    Relay(PriceWorker worker) {
        this.worker = worker;
    }

    public void relay(Work work) {
        worker.process(work);
    }
}

@Service
class PriceWorker {
    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void process(Work work) {
        // 현재 원본을 읽고 계산 결과와 작업 상태를 반영
    }
}
```

이 예제는 실제 공통 처리기 코드를 복사한 것이 아닙니다. 내가 수정한 호출 경계가 어떤 문제를 해결하는지 보여주는 모형입니다.

커밋 이후 데이터에 접근할 수 있다는 사실도 새 쓰기 트랜잭션이 생겼다는 뜻은 아닙니다. Spring은 커밋 이후 남아 있는 트랜잭션 자원에 참여하는 쓰기가 추가 커밋으로 이어지지 않을 수 있음을 명시합니다. 따라서 listener의 실행 단계와 실제 저장 트랜잭션을 함께 확인해야 합니다. [TransactionalEventListener API](https://docs.spring.io/spring-framework/docs/current/javadoc-api/org/springframework/transaction/event/TransactionalEventListener.html)

별도 트랜잭션은 만능 격리 장치도 아닙니다. 바깥 트랜잭션이 연결을 점유한 채 새 연결을 요구하는 호출 구조라면 연결 풀과 병렬 처리량도 검토해야 합니다.

## 빠른 경로와 예약 발행 경로는 같은 작업을 설명해야 한다

즉시 처리할 때는 갱신 대상과 완료시킬 작업의 범위를 알고 있었지만, 재처리 경로에 그 정보가 빠지면 같은 계산을 하더라도 완료 상태를 맞추기 어렵습니다.

실제 후속 수정에서는 예약 발행 메시지에 누락된 처리 범위 식별자를 보완했습니다. 중요한 점은 필드를 하나 추가했다는 것보다, 두 경로가 같은 업무 단위를 표현해야 한다는 계약입니다.

설명용 메시지를 만들면 다음과 같습니다.

```json
{
  "workKey": "demo-work-17",
  "targetKey": "demo-event",
  "recalculationScope": "demo-scope"
}
```

이 값들은 실제 메시지 스키마나 회사 식별자가 아닙니다. 갱신할 대상과 처리한 작업의 범위를 구분하기 위한 합성 예제입니다.

업무 버전은 이 처리 범위와 또 다른 개념입니다. 작업 ID가 증가한다고 계산 결과의 최신성이 자동으로 보장되지는 않습니다.

## 중복 처리와 오래된 결과 덮어쓰기는 별도 문제다

Outbox와 재처리 경로는 중복 실행 가능성을 포함합니다. SQS 표준 큐 역시 메시지가 다시 전달될 수 있으므로 소비자 측 멱등성이 필요합니다. 이 일반적인 전달 성질을 큐 종류와 무관한 업무 성공 보장으로 해석해서는 안 됩니다. [SQS 최소 한 번 전달 문서](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/standard-queues-at-least-once-delivery.html)

가격을 “최신 원본으로 다시 계산해 교체”하는 작업은 단순 증가 연산보다 재실행을 다루기 쉬울 수 있습니다. 그러나 이 모양만으로 순서 역전이 없어지지는 않습니다.

```text
작업 A: 원본의 이전 상태를 읽음
작업 B: 새 상태를 읽어 새 가격을 저장
작업 A: 늦게 계산을 끝내 이전 가격을 저장
```

다음 리팩토링에서는 원본 버전과 반영 버전을 비교하는 전략을 검토하겠습니다. 계산 입력을 읽은 버전보다 원본이 앞서갔다면 결과를 버리거나 다시 계산하고, 저장 시에도 더 낮은 버전이 덮지 못하게 해야 합니다.

아래는 그 개선안을 설명하는 SQL입니다. 현재 회사 구현에 적용됐다는 뜻이 아닙니다.

```sql
-- 합성 개선 예제: 같은 결과 키에서 낮은 버전의 덮어쓰기 거절
UPDATE demo_price_result
SET displayed_value = :calculated_value,
    applied_version = :input_version
WHERE result_key = :result_key
  AND applied_version < :input_version;
```

이 조건만으로 첫 생성, 원본의 추가 변경, 작업 완료 범위까지 모두 해결되지는 않습니다. 첫 행 생성의 유일성, 동일 버전 재처리, 원본 버전 재확인과 작업 상태 기록을 함께 설계해야 합니다.

## 다음 검증은 성공 경로보다 중단 지점에 맞추겠다

이번 글은 실제 작업 기록과 구현의 트랜잭션 경계를 대조해 작성했습니다. 회사 환경에서 장애를 주입하거나 전체 큐 처리 테스트를 재실행한 결과를 포함하지 않습니다.

우선 보완할 검증은 다음과 같습니다.

1. 원본 저장이 롤백되면 Outbox도 남지 않는지 확인합니다.
2. 커밋 직후 빠른 경로를 건너뛰어도 미처리 작업을 다시 찾는지 확인합니다.
3. 같은 메시지를 반복 전달하고 결과와 작업 상태를 비교합니다.
4. 계산 결과 저장 뒤 완료 기록 실패를 주입합니다.
5. 이전·새 입력의 계산을 역순으로 끝내 최신 결과가 유지되는지 확인합니다.
6. 즉시 처리와 예약 발행이 같은 대상·범위를 전달하는지 비교합니다.

관측성도 후속 과제입니다. 실패 횟수만 세면 아주 오래 남은 작업을 놓칠 수 있습니다. 가장 오래 대기한 작업의 나이, 실패 종류, 재처리 결과를 함께 보겠습니다. 반복해도 성공하지 않는 입력은 무한 재시도 대신 별도 검토 상태와 수동 처리 절차가 필요합니다.

이 경험에서 트랜잭션과 메시지의 역할이 선명해졌습니다. 원본 저장은 무엇을 바꿨는지 확정하고, Outbox는 뒤따라야 할 작업을 기록합니다. 이후의 실행은 그 기록을 반복해서 읽을 수 있으므로, 호출 경계와 소비자 정합성까지 같은 설계 안에서 검토해야 했습니다.
