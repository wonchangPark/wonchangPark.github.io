클럽미니쉬에서 내가 주로 맡은 작업은 이벤트 도메인이었습니다. 초기 이벤트와 이벤트 템플릿 개념을 도입하고, 이벤트·가격·할인 모델과 조회·관리 API를 구현했습니다. 계산한 가격을 저장해 조회에서 사용하는 구조와, 이벤트 수정에 따라 그 결과를 다시 맞추는 Outbox 흐름도 설계했습니다.

이 설계를 이해하려면 테이블을 몇 개로 나눴는지보다 세 질문을 먼저 봐야 합니다. 무엇을 같은 상품으로 볼 것인지, 어떤 조건이 계산의 입력인지, 저장한 계산 결과가 언제까지 유효한지입니다.

아래의 공방 수업 모델과 식별자는 설명을 위해 새로 만든 합성 예제입니다. 실제 업무 모델과 가격 규칙을 그대로 옮기지 않았습니다.

## 같은 상품을 조건 수만큼 복제하면 생기는 문제

가상의 공방에 같은 도자기 수업이 있다고 하겠습니다. 일반 신청과 회원 신청에 서로 다른 조건이 붙습니다. 이를 각각 독립 이벤트로 만들면 등록 화면은 단순합니다.

```text
일반 신청 이벤트 ── 도자기 수업
회원 신청 이벤트 ── 도자기 수업
```

문제는 한 사용자가 여러 조건을 만족할 때 나타납니다. 같은 수업이 목록에 두 번 보일 수 있고, 설명을 수정할 때 두 이벤트를 함께 바꿔야 할 수도 있습니다. 리뷰나 검색 결과를 어느 단위로 묶을지도 애매해집니다.

이 때문에 템플릿을 도입했습니다. 템플릿은 여러 운영 이벤트가 같은 상품인지 판단할 기준이 됩니다. 사용자에게 보여줄 목록을 만드는 기준과 운영자가 수정할 데이터를 구분하는 출발점이기도 합니다.

단순한 설명 모델은 다음과 같습니다.

| 개념 | 답하는 질문 | 합성 예제 |
| --- | --- | --- |
| Template | 무엇을 같은 상품으로 묶는가? | 도자기 수업이라는 상품 그룹 |
| Event | 어떤 운영 단위를 수정하는가? | 특정 기간에 열리는 수업 |
| Calculation input | 어떤 조건으로 가격을 구하는가? | 기본값과 적용 가능한 조건 |
| Stored price | 조회에 사용할 계산 결과는 무엇인가? | 계산한 표시값과 적용 근거 |

이 표의 네 개념이 실제로 네 개 테이블이어야 한다는 뜻은 아닙니다. 특히 마지막 두 개념은 데이터의 수명과 변경 책임을 설명하기 위한 구분입니다.

## 템플릿에 공통값을 모으는 것만으로는 부족했다

처음에는 이름, 설명, 가격 같은 값을 템플릿에 모으면 중복 수정이 줄어들 것으로 생각하기 쉽습니다. 하지만 공통으로 보이는 값도 운영 단위에 따라 달라질 수 있습니다.

같은 수업이어도 기간별 설명이 다르거나 운영 조건에 따라 표시값이 달라지면, 템플릿의 값을 바꾸는 작업이 다른 이벤트까지 영향을 줍니다. 반대로 템플릿의 값을 이벤트마다 복사하면 어느 값이 기준인지 다시 정해야 합니다.

기존 설계 과정에서도 템플릿에 많은 값을 둔 경계가 문제였고, 운영 요구에 맞춰 이벤트 쪽으로 책임을 옮기는 판단이 있었습니다. 여기서 얻은 기준은 “여러 행에 같으니 공통 테이블로 옮긴다”보다 구체적입니다.

- 함께 바뀌어야 하는 값은 같은 변경 경계에 둡니다.
- 서로 다르게 바뀔 수 있는 값은 운영 단위가 소유하게 합니다.
- 같은 상품이라는 식별 관계와 현재 보여줄 값을 구분합니다.

템플릿 중심 모델을 도입했다는 사실과 현재 모든 값을 템플릿이 소유한다는 주장은 다릅니다. 템플릿은 도메인을 이해하는 데 필요한 개념이지만, 어떤 값까지 소유할지는 요구사항에 따라 바뀔 수 있습니다.

다시 설계한다면 템플릿을 얇은 상품 그룹으로 유지하고, 운영 정보와 적용 조건의 경계를 더 명확히 검토하겠습니다. 이 재구성은 개선안이며 전체가 적용된 현재 구조로 설명하지 않습니다.

## 조회마다 계산할지, 계산 결과를 저장할지

가격 계산에는 입력 조건을 모으고 규칙을 적용하는 책임이 있습니다. 이 책임을 목록 응답을 만들 때마다 반복할 수도 있고, 변경 시 계산한 결과를 저장해 조회에서 사용할 수도 있습니다.

| 방식 | 장점 | 함께 부담하는 비용 |
| --- | --- | --- |
| 조회 시 계산 | 읽는 시점의 입력으로 계산할 수 있음 | 조회 경로가 계산과 입력 조회에 결합됨 |
| 명령 트랜잭션 안에서 계산·저장 | 원본과 결과를 한 번에 확정하기 쉬움 | 계산 실패와 시간이 원본 저장에 영향을 줌 |
| 변경 기록 후 별도로 계산·저장 | 조회와 계산 책임, 실패 범위를 나눌 수 있음 | 갱신 지연·누락·중복을 관리해야 함 |

이벤트 도메인에서는 계산한 가격과 적용된 할인 정보를 저장해 조회에서 활용했습니다. 따라서 저장 가격은 원본 자체라기보다 원본과 규칙으로부터 만들어진 읽기용 결과입니다.

다음처럼 설명할 수 있습니다.

```text
이벤트와 적용 조건
  -> 공통 가격 계산 책임
  -> 계산된 가격·적용 근거 저장
  -> 목록·상세 응답에 맞춘 조회와 조립
```

저장하면 조회에서 매번 모든 계산을 할 필요가 줄어듭니다. 대신 원본이 바뀌는 순간 결과가 오래된 상태가 될 수 있습니다. 계산 결과 저장은 조회 편의와 갱신 책임을 함께 선택하는 일입니다.

이 선택만으로 실제 응답시간이 얼마나 줄었다고 주장할 수는 없습니다. 이 글에서 확인할 결과는 계산 책임과 조회 책임을 나눴다는 구현상의 변화입니다.

## 계산 규칙이 여러 계층에 흩어지지 않도록 했다

가격을 저장한다고 계산 규칙의 중복이 사라지는 것은 아닙니다. 목록, 상세, 응답 조립 과정에서 같은 규칙을 따로 구현하면 한 경로만 수정되는 문제가 생깁니다.

실제 작업에서는 조회와 명령 서비스를 분리하고, 공통 할인 계산 책임을 모았습니다. 조회에 필요한 projection을 조립하는 책임과 그것을 외부 응답으로 바꾸는 책임도 나눴습니다.

설명용 호출 흐름은 다음과 같습니다.

```text
Command
  -> 변경 가능 여부 검사
  -> 이벤트 변경
  -> 가격 갱신 작업 기록

Calculator
  -> 입력 조건 해석
  -> 공통 계산 규칙 적용
  -> 계산 결과 생성

Query
  -> 필요한 원본·저장 결과 조회
  -> 조회용 projection 조립

Response assembler
  -> API 표현으로 변환
```

이 구분을 읽기 저장소와 쓰기 저장소를 완전히 분리한 아키텍처로 확대할 필요는 없습니다. 핵심은 서로 다른 책임이 같은 규칙을 제각각 소유하지 않도록 하는 것입니다.

계산기가 응답 DTO까지 만들면 화면이 바뀔 때 계산 코드가 함께 바뀝니다. 응답 조립기가 규칙을 다시 계산하면 그곳이 두 번째 계산기가 됩니다. 책임을 나누는 기준은 클래스 수가 아니라 변경 이유입니다.

## 같은 상품으로 묶는 것과 결과를 하나로 고르는 것도 다르다

템플릿으로 같은 상품을 묶었다고 목록의 최종 카드가 자동으로 정해지지는 않습니다. 사용자가 여러 이벤트 조건을 만족할 때 어떤 결과를 보여줄지 별도의 규칙이 필요합니다.

아래는 그 차이를 보여주는 합성 데이터입니다.

```json
[
  {
    "templateKey": "craft-class",
    "offerKey": "general",
    "eligible": true,
    "calculatedLabel": "일반 신청"
  },
  {
    "templateKey": "craft-class",
    "offerKey": "member",
    "eligible": true,
    "calculatedLabel": "회원 신청"
  }
]
```

그룹 키만으로 중복 행을 지우면 어떤 조건을 선택했는지 설명할 수 없습니다. 가격만 비교해 고르면 동률이나 적용 제한을 다루기 어렵습니다. “같은 상품”과 “최종 선택된 조건”은 서로 다른 판단입니다.

다시 조회 모델을 구성한다면 먼저 적용 가능한 후보를 모으고, 명시적인 선택 규칙으로 결과와 근거를 함께 만들겠습니다. 동률의 결정 기준도 데이터 계약에 넣어야 합니다. 이 선택 모델은 설명용 개선안이며 회사의 실제 우선순위 규칙을 공개하는 예제가 아닙니다.

## 저장한 가격의 갱신도 이벤트 변경의 일부다

이벤트를 수정한 뒤 가격을 다시 계산해야 한다면 두 작업 사이에 실패 지점이 생깁니다. 이벤트는 저장됐는데 계산 요청이 사라질 수 있고, 계산 요청이 중복으로 전달될 수도 있습니다.

그래서 이벤트 수정 시 가격 갱신 작업을 Outbox에 기록하고, 커밋 이후 처리와 미처리 작업의 재처리 경로로 연결했습니다. 원본 변경과 “갱신이 필요하다”는 기록을 함께 남기는 것이 핵심입니다.

구체적인 트랜잭션 경계와 중복 처리 문제는 [저장 가격을 Outbox로 갱신한 글](/posts/outbox-sqs-price-recalculation/)에서 설명합니다. 승인 전 변경 요청과 실제 운영 데이터를 분리한 이야기는 [이벤트 검수 설계 글](/posts/event-approval-jsonb-snapshot/)로 이어집니다.

여기에는 후속 계약이 하나 더 필요합니다. 갱신이 끝나기 전 사용자에게 어떤 상태를 보여줄 것인지입니다. 이전 값을 계속 보여줄지, 갱신 중으로 표시할지, 중요한 결정 시점에는 다시 검증할지에 따라 제품 동작이 달라집니다. 저장 가격을 최종 업무 결정에 사용할 때의 최신성 계약은 별도로 검토해야 합니다.

## 검증은 테이블 모양보다 불변식에 맞춰야 한다

이번 회고에서는 이벤트·가격 저장과 계산 책임 분리, Outbox 연결을 구현 및 변경 기록으로 확인했습니다. 회사 환경의 전체 테스트와 성능 측정은 이 글을 위해 다시 실행하지 않았습니다.

다음에 우선 검증할 것은 다음과 같은 계약입니다.

| 검증 상황 | 확인할 조건 |
| --- | --- |
| 동일 입력을 목록과 상세에서 사용 | 공통 계산 결과가 계층에 따라 달라지지 않음 |
| 사용자가 여러 조건을 만족 | 묶는 기준과 최종 선택 근거가 명확함 |
| 한 운영 이벤트의 설명을 변경 | 다른 운영 단위의 값이 의도치 않게 바뀌지 않음 |
| 이벤트 변경 뒤 계산 실패 | 원본 변경과 갱신 필요 기록이 함께 남음 |
| 오래된 계산 작업이 늦게 도착 | 이미 반영한 새 결과를 덮지 않는 전략이 있음 |

마지막 행은 개선 검증 대상입니다. Outbox가 있다는 사실만으로 버전 역전까지 해결된 것으로 보지는 않습니다.

내가 이 작업에서 배운 것은 템플릿, 계산기, 읽기 모델을 각각 도입하는 것보다 그 사이의 계약을 설명하는 일이 중요하다는 점입니다. 상품을 묶는 기준을 세우고, 계산한 값을 저장한 다음에는 그 값이 변경을 어떻게 따라오는지까지 도메인 설계에 포함해야 했습니다.
